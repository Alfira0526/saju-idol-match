# 개선 제안 백로그 (상세 실행안)

주간 운영 리뷰(§4)가 낸 제안을 **실행 가능한 스펙**으로 구체화한 살아있는 문서.
각 제안은 아래 필드를 반드시 채운다: 배경 · 목표(측정가능) · 구체 변경안(파일·방식) ·
단계/공수 · 예상효과 · 리스크 · **결정 필요** · 상태.

> 상태 표기: `제안`(승인 대기) → `승인` → `진행` → `완료`. 큰 변경은 사용자 승인 전
> 코드/데이터에 반영하지 않는다(OPS_ROUTINES 안전규칙).

## P3 · Flush 배치 급증 원인 구분(관찰용 계측)
**상태: ✅ 완료 — 3A 구현(2026-07-27) · 3B(워커 로깅)는 보류 · 우선순위: 완료**

> **결정:** 3A만. `ops-metrics.js`에 `flushCadence`(최근 7일 `chore(inbox): flush` 커밋의
> 간격·배치 분석) 구현 완료 — `gap>20m→cron-delay` / `gap≈10m·batch>15→inflow-surge`로
> 자동 분류. 첫 산출에서 19:10 batch 31(gap 10)=inflow-surge, gap 120·220m=cron-delay(오늘
> Cron 등록 전 수동 flush 흔적)를 구분 확인. 3B(워커 lastFlushAt 로깅·재배포)는 필요 시로 보류.

- **배경.** 7/27 19:00~19:40 flush 배치가 29/31/38건으로 평소(1~6) 대비 급증. 데이터 무결성
  영향은 없으나(카운트 동기화), 원인이 **①제보 유입 폭주** vs **②Cron 지연 누적**인지 미구분.
- **목표.** 두 원인을 **구분 가능한 지표** 확보 → 유입 폭주면 무해, Cron 지연이면 워커 점검.
- **구체 변경안 — 2안(저리스크 우선).**
  - **3A — 저장소 측 분석(권장, 인프라 변경 0).** `tools/ops-metrics.js`에 `flushCadence`
    지표 추가: 최근 N일 `git log`에서 `chore(inbox): flush …` 커밋의 **타임스탬프 간격**과
    **배치 크기**를 계산. 판정 규칙 = *간격≈10분인데 배치 큼 → 유입 폭주 / 간격≫10분(지연)
    → Cron 지연*. 급증 구간(배치>15 또는 간격>20분)을 리포트에 자동 표기. **워커 재배포 불필요.**
  - **3B — 워커 측 로깅(선택, 승인+재배포).** `worker/suggest-worker.js` `flush()`에 KV
    `lastFlushAt` 저장 → 다음 flush에서 `gap=now-lastFlushAt` 계산해 커밋 메시지에 부기
    (`flush N add (gap 12m, q=N)`) 또는 Workers Logs(console)로 출력. 소량 변경이나 **재배포
    필요**(사용자가 방금 익힌 Edit code→Deploy 절차).
- **단계/공수.** 3A: ops-metrics.js에 함수 1개(약 30분), 즉시 적용 가능·리스크 0. 3B: 워커
  10줄 + 재배포.
- **예상효과.** 다음 급증 시 원인 자동 판별 → 불필요한 워커 점검/오탐 방지.
- **리스크.** 3A 없음(읽기 전용 git log 분석). 3B 낮음(재배포 필요).
- **⚠️ 결정 필요.** 3A만으로 충분한지(권장) / 3B까지 필요한지. **3A는 저리스크라 승인 시
  이번에 바로 구현 가능.**
