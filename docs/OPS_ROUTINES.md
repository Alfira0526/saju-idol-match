# OPS_ROUTINES — 운영 루틴 프로세스 정의

이 문서는 saju-idol-match의 **자동 운영 루틴**이 따르는 프로세스를 정의한다.
작업 브랜치: `claude/idol-saju-matching-app-752fy3`. 조직 체계는
[`team-personas.md`](./team-personas.md)(5인 페르소나), 품질 게이트는
[`../tools/qa-checklist.md`](../tools/qa-checklist.md), 데이터 파이프라인은
[`../tools/README.md`](../tools/README.md)를 따른다.

## 루틴 3종 (역할 분리)
| 루틴 | 주기 | 역할 |
|---|---|---|
| **일일 데이터 업데이트** | 매일 23:00 KST | 제보 반영(오류→추가) + 요일 고정 태스크(월·수·금 B / 화·토 A / 목·일 C). 상세: `tools/README.md` |
| **데이터 헬스체크** | 매일 03:00 KST | build·스모크·정합성 점검, 판단 필요한 문제는 **보고만** |
| **주간 운영 리뷰(5인 페르소나)** | 매주 월 13:00 KST | 지표 스냅샷 + 페르소나 리뷰 + 개선 제안 + 확증 오류 수정. **본 문서가 정의** |

일일/헬스체크는 "매일의 손", 주간 리뷰는 "매주의 눈" — 일일 그라인드가 놓치는
**추세·구조·사용자 경험**을 본다.

## 주간 운영 리뷰 — 절차

### 0) 데이터 소스 (모두 저장소 로컬 파일 — 워커 접속 안 함, egress 차단)
- `docs/ops/metrics-latest.json` — **`node tools/ops-metrics.js`로 생성**하는 지표
  스냅샷(데이터 규모·커버리지·정합성·백로그·i18n 진척). *이 앱은 정적 사이트라
  이용률/정답률 같은 사용 분석이 없으므로, 지표는 저장소에서 계산한 데이터 건강 지표다.*
- `docs/ops/SNAPSHOT.md` — 운영 스냅샷(직전 상태·상시 이슈·결정 로그). 리뷰가 **읽고 갱신**.
- `tools/inbox.json`(추가 제보) · `tools/error-inbox.json`(오류 제보) · `tools/inbox-done.json`
  (처리 완료 key). 제보 소스는 워커가 미러링한 로컬 파일.
- 없거나 비면 **"데이터 없음"** 으로 처리하고 그 사실을 리포트에 남긴다.

### 1) 최신화
`git fetch origin <branch> && git checkout <branch> && git pull`. 이 브랜치의 PR이
병합됐으면 기본 브랜치에서 같은 이름으로 재시작.

### 2) 지표 생성·읽기
`node tools/ops-metrics.js`(오늘 날짜는 `--date=YYYY-MM-DD`로 넘길 수 있음) →
`docs/ops/metrics-latest.json` 갱신. 그 값과 `docs/ops/SNAPSHOT.md`를 읽는다.

### 3) 5인 페르소나 리뷰 (역할·관계는 team-personas.md 준수)
- **팀장(8년차)** = 분배·의견 종합·**최종 판단**(“경우에 따라” 금지, 명확한 권고).
- **QA(4년차)** = 정합성(`statsTotalMatches`·중복 0)·제보 백로그 정리·회귀·엣지케이스.
- **개발자(4년차)** = 시스템/파이프라인(워커 큐→cron flush 정상, 커밋 폭증 여부, build·성능).
- **기획자(4년차)** = 재미 요소·**최초 기획의도 유지**(사전지식 없이 오로지 사주 특성만으로
  오락적 최애 추천 + 순위·이유).
- **디자이너(3년차)** = UX/사용자 친화(정보 위계·첫 진입 마찰·모바일).

각 페르소나는 metrics/SNAPSHOT을 자기 렌즈로 보고 **동의/충돌/놓친 점**을 낸다 →
팀장이 종합해 **판정·권고**.

### 4) 오류·이상 후보 교차검증 (WebSearch)
- `error-inbox.json`의 미처리 오류 제보, 그리고 리뷰 중 발견한 **이상 후보**(예: 특정
  카테고리가 오래 30 문턱 미달, 특정 그룹 데이터 이상)를 **WebSearch로 교차검증**한다.
- **확증된 데이터 오류만** `tools/idols.json`에서 즉시 수정(생일·활동명·그룹·성별 정정,
  비실존·중복 삭제). 신고 제안값은 참고만(맹신 금지) — 독립 출처로 확인될 때만.
- 처리(반영·오신고 정리)한 제보 `key`를 **`tools/inbox-done.json`에 추가**(일일 루틴과
  동일 파일 — 재처리 방지). `WebFetch`/`curl` 임의 접속 금지, `WebSearch`만.

### 5) 리포트 작성
`docs/reports/<YYYY-MM-DD>-review.md` 작성(양식: [`../reports/README.md`](reports/README.md)):
지표 요약 · 오류 처리 내역 · 개선 제안 · 신규 데이터/기능 아이디어.
그리고 `docs/ops/SNAPSHOT.md`의 헤드라인 수치·상시 이슈·결정 로그를 갱신한다.

**개선 제안은 반드시 실행 가능한 스펙으로 쓴다(“재확인/검토” 같은 메타 서술 금지).**
각 제안은 아래 필드를 채워 [`ops/PROPOSALS.md`](ops/PROPOSALS.md)에 신규 항목으로
추가(또는 기존 항목 상태 갱신)하고, 리포트 §4에는 그 요약 + PROPOSALS 링크만 남긴다:
- **배경**(수치 포함) · **목표**(측정 가능) · **구체 변경안**(어느 파일·어떤 방식·코드 지점) ·
  **단계/공수**(안전한 데이터 단계 vs 승인 필요한 코드 단계 분리) · **예상효과** ·
  **리스크**(해당 안전규칙) · **결정 필요**(사용자가 골라야 할 선택지) · **상태**.
- 읽는 사람이 “어느 부분을 어떻게 바꾸는지” 코드를 안 봐도 이해되게 쓴다.

### 6) 검증 후 커밋·푸시
데이터/UI 변경이 있으면 **`node tools/build.js` 통과 + 헤드리스 스모크(JS 에러 0) +
`tools/qa-checklist.md` 해당 항목** 통과. 모두 통과할 때만 커밋(명확한 메시지)하고
**작업 브랜치에만** push(원격 새 커밋 있으면 rebase — 워커·일일 루틴이 커밋했을 수 있음).
리포트·metrics·SNAPSHOT만 바뀐 경우엔 build 없이 커밋 가능(코드·데이터 무변경).

### 7) 주간 요약 보고 (한국어)
처리한 오류 수 · 주요 지표(총원/백로그/커버리지/i18n) · 제안 목록을 3~6줄로 보고.

## 안전 규칙 (엄수)
1. **확증된 데이터 오류만** 자동 수정. 애매하거나 큰 변경(신규 기능·UX 리뉴얼·리스크
   있는 리팩터)은 직접 반영하지 말고 리포트에 **'제안'으로만** 남기고 사용자 승인 대기.
2. 작업 브랜치에만 push. **`main`·다른 브랜치 push 금지. PR 생성 금지.**
3. 커밋 메시지에 **모델 식별자 포함 금지**.
4. 웹 조사는 `WebSearch`만(egress 우회 금지). 워커에는 접속하지 않는다.
5. 증분은 작게. 출처 확실한 것만. 생일 지어내지 말 것.
